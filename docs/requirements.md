# GoEcho — Требования к системе

## 1. Общее описание

**GoEcho** — мессенджер с обменом сообщениями в реальном времени, разрабатываемый на Go.

Цель проекта — создать надёжный backend мессенджера с постоянным хранением сообщений, обменом данными в реальном времени и расширяемой архитектурой.

Первая версия ориентирована на личные диалоги и текстовые сообщения. Архитектура должна позволять добавлять новые функции и инфраструктурные компоненты без необходимости переписывать основную бизнес-логику.

## 2. Цели проекта

Цели MVP:

- Реализовать регистрацию и авторизацию пользователей.
- Поддержать личные диалоги между двумя пользователями.
- Обеспечить отправку и получение сообщений в реальном времени.
- Обеспечить постоянное хранение сообщений и истории диалогов.
- Позволить получать сообщения, пропущенные во время отсутствия пользователя в сети.
- Поддержать подтверждения доставки и прочтения сообщений.
- Предоставить документированные REST API и WebSocket-протокол.
- Обеспечить разделение бизнес-логики и инфраструктуры.
- Реализовать автоматизированные тесты, миграции БД и воспроизводимое локальное окружение.

## 3. Границы проекта

### 3.1. Входит в MVP

- Регистрация и авторизация пользователей.
- Получение профиля пользователя.
- Поиск пользователей по имени.
- Создание и получение списка личных диалогов.
- Получение списка участников диалога.
- Отправка и получение текстовых сообщений.
- Получение истории сообщений с пагинацией.
- Переподключение после потери соединения.
- Синхронизация сообщений, пропущенных во время отсутствия пользователя.
- Отслеживание статусов доставки и прочтения.
- Управление WebSocket-соединениями.
- Авторизация REST API и WebSocket-соединений.
- Валидация входных данных и проверка прав доступа.
- Структурированные логи и проверки состояния приложения.
- Миграции базы данных и автоматизированные тесты.
- Локальный запуск через Docker.

### 3.2. Не входит в MVP

Следующие функции откладываются на будущие версии:

- Групповые диалоги.
- Отправка изображений, видео, аудио и файлов.
- Голосовые и видеозвонки.
- Редактирование и удаление сообщений.
- Реакции и ответы на сообщения.
- Полнотекстовый поиск по истории сообщений.
- Push-уведомления.
- Сквозное шифрование (End-to-End Encryption).
- Автоматическое удаление сообщений по истечении срока хранения.
- Полноценная синхронизация состояния между несколькими устройствами.
- Публичный API для сторонних интеграций.
- Разделение приложения на микросервисы.
- Развёртывание в нескольких регионах.

Эти функции могут быть добавлены в следующих итерациях.

## 4. Роли пользователей

### 4.1. Неавторизованный пользователь

Неавторизованный пользователь может:

- Зарегистрировать аккаунт.
- Авторизоваться.
- Получать ошибки валидации и авторизации.

Неавторизованный пользователь не может получать доступ к защищённым ресурсам или устанавливать авторизованное соединение для обмена сообщениями.

### 4.2. Авторизованный пользователь

Авторизованный пользователь может:

- Получать собственный профиль.
- Искать других пользователей.
- Создавать диалоги с другими пользователями.
- Получать список своих диалогов.
- Получать список участников диалога.
- Запрашивать историю сообщений доступных ему диалогов.
- Отправлять и получать сообщения.
- Получать подтверждения для отправленных сообщений.
- Отмечать полученные сообщения как прочитанные.
- Переподключаться и синхронизировать пропущенные сообщения.

Пользователь не должен иметь доступа к диалогам и сообщениям, на которые у него нет прав.

## 5. Функциональные требования

### FR-01. Регистрация пользователей

Система должна позволять новому пользователю зарегистрироваться с уникальным именем пользователя и паролем.

Требования:

- Имя пользователя должно соответствовать установленным правилам валидации.
- Пароли не должны храниться в открытом виде.
- Пароли должны хешироваться с использованием подходящего алгоритма для хранения паролей.
- Повторная регистрация с уже занятым именем пользователя должна отклоняться.
- Некорректные данные должны приводить к документированной ошибке.

### FR-02. Авторизация

Система должна позволять пользователям входить в аккаунт с использованием учётных данных.

Требования:

- При успешной авторизации система должна создавать сессию или выдавать токен доступа.
- Защищённые REST endpoints должны требовать авторизацию.
- WebSocket-соединения должны проходить авторизацию.
- Некорректные или просроченные учётные данные должны отклоняться.
- Секреты и токены авторизации не должны попадать в логи.

Конкретный механизм авторизации будет определён при проектировании архитектуры.

### FR-03. Профили и поиск пользователей

Система должна позволять авторизованному пользователю получать собственный профиль.

Также система должна поддерживать поиск пользователей по имени.

Требования:

- Поиск не должен раскрывать хеши паролей и другие секреты авторизации.
- Ответы должны содержать только разрешённые для выдачи поля.
- Поведение при отсутствии пользователя и некорректном запросе должно быть определено явно.

### FR-04. Диалоги

Система должна поддерживать личные диалоги между двумя пользователями.

Требования:

- Авторизованный пользователь должен иметь возможность создать диалог с другим пользователем.
- Пользователь не может создать диалог с самим собой.
- Только участники диалога могут получать его историю и отправлять сообщения.
- Пользователь должен иметь возможность получить список своих диалогов.
- Информация о диалогах должна сохраняться в базе данных.
- Политика обработки повторного создания диалога между одной и той же парой пользователей должна быть определена явно.

Правила уникальности личных диалогов будут окончательно определены при проектировании модели данных.

### FR-05. Отправка сообщений

Система должна позволять авторизованному участнику диалога отправлять текстовые сообщения.

Требования:

- Каждое сообщение должно принадлежать определённому диалогу.
- Каждое сообщение должно содержать идентификатор отправителя.
- Сервер должен проверять содержимое и размер сообщения.
- Сообщение должно быть сохранено в базе данных до подтверждения успешного принятия.
- Каждое принятое сообщение должно иметь уникальный идентификатор и время создания, назначенное сервером.
- Пользователь не должен отправлять сообщения в диалоги, участником которых он не является.
- Протокол должен поддерживать идентификацию повторных отправок со стороны клиента.
- Повторный запрос с тем же идентификатором идемпотентности не должен создавать дубликат сообщения в пределах установленной области действия этого идентификатора.

Максимальный размер сообщения и срок действия идентификатора идемпотентности будут определены при проектировании API.

### FR-06. Доставка сообщений в реальном времени

Система должна доставлять новые сообщения получателям с активными WebSocket-соединениями.

Требования:

- Клиент должен иметь возможность установить авторизованное WebSocket-соединение.
- Сервер должен проверять входящие события.
- Входящие события должны соответствовать документированному протоколу.
- Сервер должен направлять сообщения только разрешённым получателям.
- Отправитель должен получать подтверждение после успешного сохранения сообщения.
- Получатель должен получать событие с сохранённым представлением сообщения.
- Отключение получателя не должно приводить к потере уже сохранённых сообщений.

Успешное сохранение сообщения и успешная доставка получателю являются разными событиями.

### FR-07. История сообщений

Система должна предоставлять доступ к сохранённой истории диалогов.

Требования:

- Историю могут получать только участники соответствующего диалога.
- История должна поддерживать пагинацию.
- Порядок сообщений должен быть детерминированным.
- Пагинация должна обеспечивать корректное получение новых сообщений по мере их появления.
- Клиент должен иметь возможность запросить сообщения после известного идентификатора или другого курсора.
- База данных должна обеспечивать эффективное получение последних сообщений диалога.

Для первой версии предпочтительна пагинация по курсору (cursor-based pagination).

### FR-08. Переподключение и синхронизация

Система должна поддерживать восстановление работы после временного отключения клиента.

Требования:

- Клиент должен иметь возможность повторно установить авторизованное соединение.
- Клиент должен иметь возможность определить, какие сообщения он уже обработал.
- После переподключения клиент должен иметь возможность получить пропущенные сообщения.
- Повторную доставку одного сообщения клиент должен уметь распознавать.
- Источником истины при синхронизации должны быть сохранённые данные.

Первая версия не гарантирует непрерывную доставку при отключённом клиенте, но гарантирует возможность получить сохранённые сообщения после переподключения.

### FR-09. Статусы сообщений

Система должна различать принятие, доставку и прочтение сообщения.

Определения:

- **Принято (Accepted):** сообщение проверено и сохранено сервером.
- **Доставлено (Delivered):** клиент получателя подтвердил получение сообщения.
- **Прочитано (Read):** получатель явно подтвердил прочтение сообщения.

Требования:

- Отправитель должен иметь возможность определить, было ли сообщение принято сервером.
- Статусы доставки и прочтения должны быть связаны с соответствующим сообщением и получателем.
- Обновление статусов должно проходить проверку прав доступа.
- Повторные подтверждения должны обрабатываться идемпотентно.

Способ хранения статусов доставки и прочтения будет определён при проектировании модели данных.

### FR-10. Обработка ошибок

Система должна возвращать предсказуемые ошибки.

Требования:

- Ошибки REST API должны использовать документированные HTTP-коды и единый формат ответа.
- Ошибки WebSocket должны иметь документированные типы событий и коды ошибок.
- Некорректные данные должны отклоняться.
- Ошибки доступа не должны раскрывать защищённую информацию о диалогах.
- Внутренние ошибки не должны раскрывать клиенту stack trace, учётные данные или подробности работы базы данных.
- Ошибки должны логироваться с достаточным контекстом для отладки без записи чувствительных данных.

### FR-11. Жизненный цикл соединений

Система должна безопасно управлять активными WebSocket-соединениями.

Требования:

- Сервер должен обнаруживать закрытые соединения.
- После отключения должны освобождаться связанные ресурсы.
- Операции с соединениями должны быть безопасны при конкурентном выполнении.
- Реализация не должна допускать конкурентную запись в один WebSocket без поддержки этого со стороны выбранной библиотеки.
- Сервер должен поддерживать heartbeat или другой механизм обнаружения неактивных соединений.
- Сервер должен поддерживать корректное завершение работы (graceful shutdown).

Конкретные ограничения на количество соединений и значения таймаутов будут определены при реализации и тестировании.

## 6. Требования к данным

### 6.1. Постоянно хранимые данные

Начальная модель данных должна поддерживать хранение следующих сущностей:

- Пользователи.
- Диалоги.
- Участники диалогов.
- Сообщения.
- Статусы доставки и прочтения, включая состояние конкретного получателя, если это необходимо.

PostgreSQL предлагается использовать в качестве основной базы данных и источника истины для постоянных данных приложения.

### 6.2. Целостность данных

Требования:

- Постоянно хранимые сущности должны иметь стабильные уникальные идентификаторы.
- Связи между сущностями должны защищаться соответствующими ограничениями БД.
- Обязательные поля не должны допускать недопустимые значения NULL.
- Уникальность должна обеспечиваться ограничениями базы данных там, где это необходимо.
- Создание сообщения и связанные изменения состояния должны выполняться в транзакции, если требуется атомарность.
- Изменения схемы БД должны управляться версионируемыми миграциями.

### 6.3. Порядок сообщений

Система должна обеспечивать детерминированный порядок сообщений внутри диалога.

Проектирование должно учитывать сообщения, созданные почти одновременно. Временная метка сама по себе не должна считаться гарантией уникального порядка.

Окончательная стратегия сортировки и пагинации будет определена при проектировании модели данных.

### 6.4. Хранение данных

История сообщений должна оставаться доступной после перезапуска приложения.

В MVP не определяются автоматическое удаление сообщений и политики истечения срока хранения. До production-развёртывания необходимо описать резервное копирование и восстановление данных.

## 7. Требования к API и протоколам

### 7.1. REST API

REST API должен:

- Использовать HTTP и JSON.
- Иметь версионируемый префикс URL, первоначально `/v1`.
- Определять схемы запросов и ответов.
- Документировать требования к авторизации.
- Документировать правила валидации и форматы ошибок.
- Поддерживать пагинацию для коллекций.
- Иметь спецификацию OpenAPI.

### 7.2. WebSocket-протокол

WebSocket-протокол должен:

- Использовать авторизованное соединение.
- Определять единый формат события.
- Содержать тип события и полезную нагрузку (payload).
- Поддерживать идентификаторы корреляции запросов там, где это необходимо.
- Определять события подтверждения и ошибки.
- Определять идентификаторы сообщений и правила идемпотентности.
- Определять heartbeat и поведение при закрытии соединения.
- Определять правила переподключения и синхронизации.
- Определять правила валидации и ограничения размера сообщений.

Для первой версии в качестве формата WebSocket-сообщений предлагается JSON.

Точные названия событий и схемы payload будут описаны отдельно в `docs/api/websocket.md`.

### 7.3. Внутренние интерфейсы

Сценарии приложения (use cases) не должны напрямую зависеть от деталей HTTP, WebSocket или конкретной реализации базы данных.

Доступ к инфраструктуре должен осуществляться через подходящие интерфейсы.

REST API и WebSocket должны использовать общие бизнес-правила приложения, а не реализовывать отдельные версии одних и тех же сценариев.

## 8. Нефункциональные требования

### NFR-01. Надёжность

- Сохранённые сообщения должны переживать перезапуск процесса приложения при соблюдении настроек надёжности и восстановления базы данных.
- Временное отключение получателя не должно делать сохранённые сообщения недоступными.
- Временные ошибки доставки должны компенсироваться синхронизацией истории.
- Система должна различать гарантии сохранения и гарантии доставки в реальном времени.

### NFR-02. Согласованность данных

- PostgreSQL является источником истины для пользователей, диалогов и сохранённых сообщений.
- Сервер не должен подтверждать успешное сохранение до фиксации транзакции базы данных.
- Операции, требующие атомарного изменения нескольких данных, должны использовать транзакции.
- Если сообщение сохранено, но немедленная доставка не удалась, оно должно оставаться доступным для получения.

### NFR-03. Безопасность

- Пароли должны храниться в виде безопасных хешей.
- Защищённые операции должны требовать действующей авторизации.
- Для каждой операции с диалогом должна проверяться принадлежность пользователя к нему.
- Входные данные должны проходить валидацию.
- Сервер должен ограничивать размер сообщений и частоту запросов.
- Чувствительные данные не должны раскрываться в логах и ответах об ошибках.
- В production-трафике должен использоваться TLS.
- Проверка WebSocket Origin должна соответствовать явно заданной политике для используемых типов клиентов.

### NFR-04. Безопасность конкурентного выполнения

- Конкурентные запросы не должны нарушать целостность данных.
- Общее состояние активных соединений в памяти должно обрабатываться потокобезопасно.
- Очистка соединений не должна приводить к гонкам данных или утечкам ресурсов.
- Приложение должно проверяться с помощью Go race detector.

### NFR-05. Поддерживаемость

- Бизнес-правила должны быть отделены от деталей инфраструктуры.
- Зависимости должны быть явными и инициализироваться в точке сборки приложения.
- Изменения схемы БД должны версионироваться.
- Основная бизнес-логика должна допускать модульное тестирование.
- Контракты API и протоколов должны храниться рядом с исходным кодом.

### NFR-06. Наблюдаемость

Приложение должно предоставлять:

- Структурированные логи.
- Endpoints проверки состояния и готовности.
- Полезный контекст ошибок без чувствительных данных.
- Базовые метрики HTTP-запросов, активных WebSocket-соединений, сохранения сообщений, ошибок доставки и ошибок базы данных.

Распределённая трассировка может быть добавлена, если она будет полезна для диагностики.

### NFR-07. Производительность и масштабирование

Архитектура MVP должна допускать возможность горизонтального масштабирования в будущем.

При этом числовые требования к пропускной способности, задержке, доступности и количеству одновременных соединений пока не определены.

До выбора и настройки дополнительной инфраструктуры необходимо определить:

- Ожидаемое количество одновременных WebSocket-соединений.
- Ожидаемое количество сообщений в секунду.
- Ожидаемый объём истории сообщений.
- Допустимую задержку доставки сообщений.
- Ожидаемый рост объёма базы данных.
- Требования к доступности и восстановлению после сбоев.

Заявления о производительности должны подтверждаться нагрузочными тестами, а не предположениями.

### NFR-08. Разработка и переносимость

- Проект должен запускаться в воспроизводимом локальном окружении через Docker Compose.
- Конфигурация должна задаваться через переменные окружения или эквивалентный механизм.
- Секреты не должны попадать в репозиторий.
- Инициализация БД и миграции должны быть воспроизводимыми.
- Приложение должно поддерживать корректное завершение работы.

## 10. Требования к тестированию

Проект должен включать:

- Модульные тесты сценариев приложения и бизнес-правил.
- Тесты авторизации и проверки прав доступа.
- Интеграционные тесты репозиториев PostgreSQL.
- Тесты миграций базы данных.
- Тесты WebSocket-протокола.
- Тесты идемпотентности сообщений и повторных подтверждений.
- Тесты переподключения и синхронизации истории.
- Тесты конкурентной обработки соединений.
- Тесты корректного завершения работы.
- Проверку гонок данных при разработке и в CI.

Обязательные сценарии:

1. Пользователь отправляет сообщение получателю, который находится в сети.
2. Пользователь отправляет сообщение, когда получатель не в сети.
3. Получатель переподключается и получает пропущенные сообщения.
4. Клиент повторяет запрос после потери подтверждения.
5. Пользователь пытается получить доступ к чужому диалогу.
6. База данных временно становится недоступна.
7. Сервер завершает работу, когда клиенты подключены.

## 11. Критерии готовности MVP

MVP считается готовым, когда:

- Пользователи могут регистрироваться и авторизовываться.
- Пользователи могут создавать и получать список личных диалогов.
- Неавторизованные участники не могут получать доступ к защищённым диалогам.
- Авторизованные пользователи могут отправлять и получать сообщения.
- Сообщения сохраняются в PostgreSQL.
- Пользователи в сети получают новые сообщения через WebSocket.
- Пользователи, отсутствовавшие в сети, могут получить сохранённые сообщения после переподключения.
- Повторные запросы с одинаковым идентификатором идемпотентности не создают дубликаты в пределах документированной области действия.
- Подтверждения доставки и прочтения соответствуют документированному протоколу.
- REST API и WebSocket-протокол документированы.
- Миграции могут инициализировать чистую базу данных.
- Автоматизированные тесты покрывают критические сценарии.
- Приложение корректно запускается и завершает работу в локальном окружении.
